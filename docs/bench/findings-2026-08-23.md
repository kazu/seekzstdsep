# Benchmark findings, 2026-08-23

All numbers are in `baseline-2026-08-23.md`; raw results in `raw/`. Measured after the one-line fix
to `cat_data` described below.

## The change

`src/seekzstdsep_lib.rs:683`, one line:

```diff
-                frames[end_frame_idx].0 + frames[end_frame_idx].1,
+                frames[end_frame_idx].0 + frames[end_frame_idx].1 - start,
```

`lines_betwee_by_separator_in_frame`'s third parameter is `frame_len` — a **length**. What was
being passed is `decomp_start + decomp_len` of the closing frame, an **absolute offset** from the
beginning of the decompressed stream. The buffer and the read were therefore sized to "everything
up to the end of the range" instead of "the range". Subtracting `start`, which is already bound to
`frames[frame_idx].0` two lines above, makes it a length.

At `--from 500000 --cnt 1` that is 65,608 bytes instead of 37,144,801.

Nothing else in `src/` was touched.

## Conditions

AMD Ryzen 9 8945HS, 16 cores, 78.4 GiB RAM, Linux 6.17. Fixture: 1,000,000 JSONL records,
74.19 MB uncompressed, 2.73 MB as seekzstdsep in 1133 frames of 884 records, 0.94 MB as plain zstd.
Matrix: `--from` at 0 / 100,000 / 250,000 / 500,000 / 750,000 / 900,000 / 999,000 x `--cnt` at
1 / 10 / 100, three engines — 63 cells, plus 2 compression cells.

| | storage | filesystem | cache |
| --- | --- | --- | --- |
| local/warm | `$HOME/.cache/seekzstdsep-bench` | XFS on nvme | warm |
| local/cold | same | XFS on nvme | cold (`fadvise`, per file) |
| nfs/warm | `$SZBENCH_NFS_DIR/…` | NFS4 | warm |
| nfs/cold | same | NFS4 | cold (`fadvise`, per file) |

Every process pinned to one CPU, `zstd --no-asyncio`, so no engine gets more of the machine than
another (`cpu / wall` is 0.99–1.00 throughout). Ten recorded rounds plus one warmup round, each
round measuring every cell once, direction alternating. Every cell's output is checked against
`uncompressed+shell`; no mismatches in any condition.

## Cost no longer depends on position

Elapsed time, ms, best of ten, local/warm:

| `--from` | `--cnt` | uncompressed+shell | seekzstdsep | zstd+shell |
| ---: | ---: | ---: | ---: | ---: |
| 0 | 1 | 0.97 | 0.82 | 1.75 |
| 100,000 | 1 | 2.18 | 0.83 | 5.77 |
| 250,000 | 1 | 4.24 | 0.97 | 10.92 |
| 500,000 | 1 | 7.58 | **0.99** | 19.46 |
| 750,000 | 1 | 10.93 | 1.04 | 27.79 |
| 900,000 | 1 | 12.69 | 1.01 | 32.97 |
| 999,000 | 1 | 13.99 | 1.10 | 36.27 |

0.82 → 1.10 ms across the whole file. The mountain is gone; what is left is a slight rise that is
within the spread (`--from 0` median 0.86, `--from 999000` median 1.18, worst values 1.01 and 1.27).
Both scanning baselines still rise linearly, because they still read the file from the front.

`--cnt` remains irrelevant: at `--from 500000`, 0.99 / 1.01 / 1.01 ms for 1 / 10 / 100 records.

Peak RSS is **3.9 MiB in all 63 cells**, against 3.9–39.1 MiB before. Bytes read from the file is
0.27 MB at every position except the last (0.15 MB), against 0.15–1.51 MB before. CPU time tracks
elapsed time (0.79–1.08 ms), so the remaining cost is process startup plus two frame
decompressions, not I/O.

For comparison, `uncompressed+shell` reads 0.02 / 7.45 / 18.57 / 37.13 / 55.66 / 66.79 / 74.14 MB
at those positions. That is the difference the format buys and the code was previously giving back.

## Where each engine wins

Elapsed time ratio, `seekzstdsep` divided by `uncompressed+shell`, `--cnt 1`. Below 1.00 means
seekzstdsep is faster:

| `--from` | local/warm | local/cold | nfs/warm | nfs/cold |
| ---: | ---: | ---: | ---: | ---: |
| 0 | 0.85x | 1.51x | 0.87x | 1.25x |
| 100,000 | 0.38x | 0.56x | 0.39x | 0.13x |
| 250,000 | 0.23x | 0.30x | 0.22x | 0.06x |
| 500,000 | 0.13x | 0.19x | 0.13x | 0.03x |
| 750,000 | 0.09x | 0.13x | 0.10x | 0.02x |
| 900,000 | 0.08x | 0.11x | 0.08x | 0.02x |
| 999,000 | 0.08x | 0.08x | 0.08x | 0.01x |

Warm, seekzstdsep wins at every measured position including record 0. Cold, it loses only at
record 0 — 1.46 ms against 0.97 ms local, 1.81 against 1.45 over NFS — where the baseline reads
one 64 kB block and seekzstdsep has to fetch the seek table plus two frames. From 100,000 onwards
it wins under every condition.

Over cold NFS the gap is what the design is for: 2.74 ms against 98.44 ms at mid-file, 36x.

Warm NFS remains indistinguishable from warm local. The page cache is the same page cache; the
mount only matters cold.

| local/warm | `seekzstdsep compress` | 49.8 ms | 4.6 MiB | 2.73 MB | 27.2x |

| local/cold | `seekzstdsep compress` | 55.4 ms | 4.6 MiB | 2.73 MB | 27.2x |

third of a single zstd stream's, the price of resetting the dictionary at every 64 kB frame.

## Still broken, outside the matrix

Both need `--cnt` beyond 100, so neither is covered by the tables above.

**`--from 999000 --cnt 10000` still panics.**

```
thread 'main' panicked at src/seekzstdsep_lib.rs:683:23:
index out of bounds: the len is 1133 but the index is 1141
```

`end_frame_idx = frames.len() * (from + cnt + 1) / total_sep_cnt` is not clamped, so asking for
more records than remain indexes past the frame table. Same line as the fix, different fault. Both
shell baselines return the 1,000 records that exist.

**`--from 999000 --cnt 1000` is fixed as a side effect.** It returned 74,181,564 bytes — 1,000
correct records followed by 74.1 MB of NUL — and now returns 74,189. The `data.len() - 1` fallback
in `lines_betwee_by_separator_in_frame` still fires when the closing separator is not found, but
the buffer it dumps is now one frame instead of the whole stream.

**`cat --cnt C` still returns C+1 records.** Visible in the `Output returned` table on every cell.

## Not measured

`cat_data` still does three things per call that scale with frame count, not with `--from`:
reading the seek table (8 bytes per frame — 9,081 bytes here, 90,529 at ten times the size),
building the full `Vec<(u64,u64)>` frame table when three entries are needed, and decompressing
frame 0 to recount records per frame. These are invisible on the position axis, which is flat, and
would only show on a file-size axis. That axis was not measured.

## Where the document and the machine disagree

`docs/benchmark.md` untouched.

**1. The fixture's three numbers cannot all hold at once.** The document says 1,000,000 records /
74.2 MB / 3.0 MB / 1096 frames at the default frame size. At 74.2 bytes per record the first frame
ends at the first record boundary at or after 65,536 bytes, which is record 884; the uniform-count
invariant fixes every later frame at 884, giving 1132 data frames plus the encoder's empty trailing
one — 1133, not 1096. 1096 frames would need ~913 records per frame, i.e. ~71.8 bytes per record
and a ~71.8 MB file. The fixture here keeps 74.19 MB and reports 1133.

**2. The compressed size is 2.73 MB, not 3.0 MB**, at 74.19 MB in with default settings.

**3. Peak RSS could not have settled the allocation question on its own.** The document called the
oversized buffer inferred rather than observed and put peak RSS on the metric list to confirm or
refute it. At mid-file it confirmed — 39.1 MiB. At `--from 999000` it read 3.9 MiB and appeared to
refute, and that appearance was false: the allocation there was 74.2 MB, visible only as
`mmap(NULL, 74174464)`. `vec![0u8; frame_len]` is lazily zeroed, so untouched pages never became
resident. Allocated was the absolute end offset everywhere; touched was
`min(end offset, EOF − frame start)`, which is what produced the mountain.

**4. `-f` is mandatory when tracing `zstd`, and `--no-asyncio` when timing it.** zstd 1.5.4+ reads
its input on a separate thread. A bytes-read measurement that does not follow threads reports zero
for `zstd -dc`; an elapsed-time comparison that leaves the thread running measures two cores
against one. Belongs with the document's rules.

**5. The recorded baseline in the document is unpinned.** Its `9.7 ms` for
`tail -n +500000 | head -n 3` is a two-process number; pinned, the same command is 7.6 ms here.
